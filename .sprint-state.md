# DAG-S24 — Corridor registry + LTP attestation verification

**Status:** in flight
**Branch:** `consensus/dag-s24-corridor-registry-and-verify`
**Base:** `main` @ `0f3b3e5` (post-S23 merge)
**Paper ref:** §10.2 (constant-size LTP commitment); IQ-002 referenced

## Goal

Close the verification gap left by S23. The LTP receiver in S23 accepted attestations unverified because no corridor registry existed in `GenesisManifest`. S24 adds:
- `CorridorConfig` / `SuperNodeConfig` schema in `GenesisManifest` (TOML; `#[serde(default)]` for backward compat)
- `State::corridors: HashMap<(ChainId, ChainId), Corridor>` loaded at startup
- `handle_ltp_attestation` looks up the corridor and calls `gsx_ltp::verify_attestation` against pinned BLS pubkeys

After S24, an inbound `CorridorAttestation` follows one of three event-log paths:

| Event | When |
|---|---|
| `verified` | Corridor in registry AND BLS aggregate verifies |
| `invalid` | Corridor in registry BUT verification fails (forged or wrong corridor) |
| `unverified` | No corridor registered for `(source, target)` — pre-S24 fallback for testnets |

## Sub-workstreams

1. **S24.1** Schema: `CorridorConfig { id, source_chain, target_chain, members }` + `SuperNodeConfig { authority, bls_public_key_hex }`. ✅
2. **S24.2** State loading: `load_corridors(manifest)` decodes hex → `gsx_ltp::Corridor`. Malformed hex drops the corridor (logged) rather than panicking at startup. ✅
3. **S24.3** Handler wires to `verify_attestation`. ✅
4. **S24.4** Smoke test: `ltp_unverified_path_when_no_corridor_registered` confirms fallback. Real verified-path test deferred (requires constructing valid BLS signatures inline).
