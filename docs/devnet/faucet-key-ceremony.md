# Faucet key ceremony

The devnet's faucet authority holds an ML-DSA-65 keypair that signs
every drip. Unlike the placeholder validator keys (which exist
because the validator-to-validator wire doesn't currently verify
ML-DSA), the faucet key MUST be real — every drip submits a signed
Transfer intent through `verify_signed_intent` on the client wire,
and that gate enforces ML-DSA-65 verification.

This document records:
1. How the initial faucet keypair was minted.
2. Where the matching public key + address lives in genesis.
3. The procedure to roll the key (e.g. on key compromise or
   periodic rotation).

## Initial minting

```sh
# Build the suwappu-keygen CLI helper (lives in suwappu-crypto):
cargo build --release -p suwappu-crypto --bin suwappu-keygen

# Generate the genesis bundle (validators + faucet authority):
./scripts/devnet/gen-genesis.py --out-dir ./target/devnet/keys

# Output:
#   target/devnet/keys/
#     genesis.toml           ← validator + faucet authority entries
#     prebalances.toml       ← faucet's initial SUWAPPU balance
#     us-east-1/{mldsa.sk,bls.sk}  ← placeholder validator keys
#     eu-west-1/...
#     ap-southeast-1/...
#     sa-east-1/...
#     faucet/mldsa.sk        ← REAL ML-DSA-65 secret (sensitive)
#     faucet/mldsa.pk        ← REAL ML-DSA-65 public
```

If `suwappu-keygen` isn't on PATH, the script emits a placeholder faucet
key and logs a loud warning. The faucet binary will reject every
drip until a real keypair is dropped in.

## Storage

The faucet secret key (`mldsa.sk`, 4032 B) is stored in AWS Secrets
Manager. The faucet EC2 instance's IAM role grants `secretsmanager:
GetSecretValue` for exactly that secret ARN and nothing else.

| Resource | Path |
|---|---|
| Secrets Manager secret | `suwappu-devnet/faucet/mldsa-secret-key` |
| Secrets Manager pubkey ref | `suwappu-devnet/faucet/mldsa-public-key` (for verification, not strictly secret) |
| S3 fallback (encrypted at rest) | `s3://suwappu-dag-devnet-artifacts/keys/faucet/mldsa.{sk,pk}` |

The S3 fallback exists because the same artifact-bucket bootstrap
that delivers per-region validator keys also delivers the faucet
key on first boot. Operators MUST rotate the S3 copy on key roll
(the Secrets Manager copy is the source of truth post-bootstrap).

## What's in genesis

`docs/devnet/genesis.toml` (committed; regenerated by
`gen-genesis.py`) declares:

```toml
[[validators]]
authority_id = 4
label = "faucet"
mldsa_public_key_hex = "<full ML-DSA-65 pubkey hex, 3904 bytes encoded as 7808 hex chars>"
bls_public_key_hex = "<placeholder; faucet doesn't sign BLS>"
validator_stake_suwappu = 1
authority_stake_suwappu = 1
```

`docs/devnet/prebalances.toml` (committed) declares the faucet's
genesis balance:

```toml
[[balances]]
address = "0x<faucet 20-byte address>"
balance_suwappu = 1000000000   # 1 billion SUWAPPU
role = "faucet"
```

The address derivation is `blake3(public_key_bytes)[..20]` — see
`suwappu_faucet::address_from_pubkey` and
`scripts/devnet/gen-genesis.py` for the matching recipe.

## Rolling the key

A faucet key roll is a four-stage operation. See OPERATIONS.md § 4
"Roll the faucet key" for the full step-by-step. Summary:

1. **Mint a new keypair** off-host (NOT on the faucet EC2):
   ```sh
   cargo run --release -p suwappu-crypto --bin suwappu-keygen -- \
     --algo mldsa --sk ./new/mldsa.sk --pk ./new/mldsa.pk
   ```

2. **Update genesis on-chain.** Submit governance Intents to
   eject the old faucet authority and admit the new one. Wait for
   the next epoch boundary so the registry change applies
   cluster-wide.

3. **Drain the old faucet wallet** via a well-known burn address
   so any leaked-key signatures can no longer drip — submit a
   Transfer of the full balance to the burn address using the OLD
   key, BEFORE the eject lands.

4. **Reconfigure the faucet service** to load the new key. Upload
   the new `mldsa.sk` to Secrets Manager, restart the
   `suwappu-faucet.service` systemd unit on the EC2 instance.

The window between step 2 (eject) and step 3 (drain) MUST be
strictly ordered — if drain races with eject, the drain can fail
because the old authority is no longer seated. Operators should
verify each step's commit before proceeding to the next.

## Threat model

The devnet's faucet handing out free tokens to anyone is *intentional*.
Threats we accept:

- **Spam.** The per-IP rate limit (`SUWAPPU_FAUCET_BUCKET_CAPACITY`,
  default 5 / `SUWAPPU_FAUCET_BUCKET_REFILL_PER_HOUR`, default 5/hour)
  caps per-source abuse at ~120 drips/day per IP. An attacker
  rotating IPs across a botnet can drain the faucet faster, but
  the faucet wallet's 1B SUWAPPU balance covers ~10M drips before
  empty.
- **Key exfiltration.** If an attacker steals the `mldsa.sk`,
  they can sign drip transfers anywhere they want. Mitigation: the
  key sits in AWS Secrets Manager with IAM scoped to the faucet
  EC2's instance role only. Operators MUST roll on suspicion.
- **Sybil drain.** Funded test addresses can be re-drained to a
  smaller set of "real" attacker addresses. We don't mitigate at
  the chain level; the per-IP bucket on the FAUCET layer is the
  only defense. For a $0-token devnet this is acceptable.

NOT in the threat model:
- Stake attacks (devnet doesn't have economic security).
- MEV / front-running (devnet has one faucet; sequencing is FIFO
  per the round driver).
- Long-range attacks / chain reorganization (devnet runs forever
  and any reorganization would invalidate dev work in flight).
